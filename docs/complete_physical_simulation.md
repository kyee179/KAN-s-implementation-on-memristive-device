# Complete physical KAN simulation notes

This document records the stricter physical simulation path added after the first hardware-aware prototype.

## What is now physically simulated

The command-line runner supports `--complete-physical`, which enables two important effects that were previously only abstracted.

1. Gilbert multiplier power generation

The trainable physical KAN no longer has to use `torch.pow(x, 3)` and `torch.pow(x, 5)` directly. In complete-physical mode, each layer generates voltage rows by cascading the Gilbert multiplier model:

```text
V1 = k*x
V2 = Gilbert(V1, V1)
V3 = Gilbert(V2, V1)
...
```

The default complete-physical run auto-calibrates `product_gain = 1/k` when no explicit gain is provided. Without that calibration, cascaded voltage products produce `(k*x)^p`, which suppresses high-order rows by extra powers of `k`. In hardware this gain would be set by multiplier bias/load or by a following row amplifier.

2. DynamicMemdiode SET/RESET programming

The pulse optimizer can now use `DynamicMemdiode.state_derivative()` for actual voltage-pulse state evolution. Gradients are still computed by KAN backpropagation, but they only decide SET/RESET polarity and pulse count. The conductance is then read back from the memdiode state and optionally quantized to the finite RRAM levels.

The physical programming controls are:

```text
--dynamic-set-voltage
--dynamic-reset-voltage
--dynamic-pulse-width-s
--max-pulses-per-update
--conductance-learning-rate
```

`--complete-physical` enables both Gilbert power generation and DynamicMemdiode pulse programming.

## Reproduce the complete-physical run

```bash
python -m kan_memristor.experiments.hardware_train \
  --datasets complicated_function taglietti_yinyang \
  --complete-physical \
  --k-values 0.2 \
  --n-train 2048 \
  --n-test 2048 \
  --pretrain-epochs 150 \
  --pulse-epochs 10 \
  --batch-size 256 \
  --n-states 64 \
  --gradient-deadzone-quantile 0.75 \
  --conductance-learning-rate 1e-10 \
  --max-pulses-per-update 2 \
  --output-dir outputs/complete_physical_training
```

The classification task remains feasible under complete physical simulation. The regression task does not: once high-order rows are generated by a saturating analog multiplier and layer outputs are fed into the next physical layer, the ideal software coefficients no longer map well.

## Important missing physical/system effects

These are the main items still missing or only approximated.

- Inter-layer voltage normalization: Mehonic et al. assume inputs to each synaptic layer are in a bounded range before multiplying by `k`. Our KAN layer outputs can be unbounded, so the next layer can overdrive the Gilbert multiplier and RRAM read range. A realistic circuit needs per-layer normalization, automatic gain control, clipping, or a bounded node nonlinearity.
- DAC/ADC and transimpedance limits: the current-to-voltage block is modeled as a fixed gain, but offset, finite resolution, saturation, bandwidth, and noise are not yet included by default.
- Crossbar parasitics: line resistance, sneak paths, wire capacitance, and source/load impedance are not modeled. The simulation assumes ideal current summation at every node.
- Device-to-device variation during programming: the mapper can inject static variability and stuck devices, but DynamicMemdiode parameters are currently shared across all devices.
- Cycle-to-cycle pulse stochasticity: identical voltage pulses are deterministic in the current model. Real programming has stochastic state changes and verify-write loops.
- Retention/endurance/drift: conductance drift over time, read disturb, endurance limits, and device aging are not included.
- Temperature and supply variation: the Gilbert multiplier and RRAM models use fixed parameters.
- Bias/sign circuitry: signed weights are differential conductance pairs. The exact subtraction circuit, common-mode current handling, and negative-voltage branch implementation are abstracted.
- Multiplier layout/resource sharing: multiplier counts are reported, but area, routing, and whether multipliers are shared across rows/columns are not yet optimized.
- Hardware-aware training before mapping: the current flow trains ideal software coefficients first, then maps them. Complete physical nonidealities are strong enough that regression likely needs hardware-in-the-loop training or calibration before pulse updates.

## Recommended next step

Add a physical normalization/calibration layer between KAN layers, then train with the complete physical forward path before mapping to pulses. This should answer whether the odd-polynomial KAN is fundamentally feasible in hardware, rather than only whether ideal coefficients survive a nonideal physical transfer function.
